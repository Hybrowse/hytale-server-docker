Local development¶

This repository is intentionally set up so contributors can test the image locally without committing or redistributing proprietary Hytale server binaries.

Prerequisites¶

  • Docker
  • Task (task): https://taskfile.dev/

Local data directory¶

The default local development workflow uses a bind mount:

  • ./data (host) -> /data (container)

This repo already ignores data/ via .gitignore.

Manual provisioning workflow¶

  1. Obtain Assets.zip and the Server/ folder:

  2. server-files.md

  3. Provision into the expected layout:

./data/
  Assets.zip
  server/
    HytaleServer.jar
    ...
  1. Start the container:
task dev:up
  1. Follow logs:
task dev:logs
  1. Stop/remove container:
task dev:down

Auto-download workflow¶

To avoid manual provisioning steps, you can start the container with auto-download enabled:

task dev:up:auto

Notes:

  • First run may require device-code authorization (watch logs).
  • Credentials will be stored on the ./data volume.
  • Auto-download currently works on linux/amd64 only.

Apple Silicon (ARM64)¶

Use the native ARM64 image for auto-download. The image includes emulation for only the official downloader; Java and the game server remain native. No --platform linux/amd64 override is required.

task dev:up:auto:amd64 is still available when you explicitly want to test the AMD64 image through emulation; it is not needed for normal ARM64 development.

Server console (interactive)¶

The Hytale server provides an interactive console while the process is running.

Attach to the console:

task dev:attach

Detach without stopping the server:

  • Press Ctrl-p then Ctrl-q

Useful variables¶

You can override these Task vars:

  • IMAGE_NAME (default hytale-server:local)
  • DEV_CONTAINER_NAME (default hytale-server-dev)
  • DEV_DATA_DIR (default ./data)
  • DEV_PORT (default 5520)

Example:

DEV_PORT=5521 task dev:up

Diagnostic checks¶

The read-only diagnostic executable is built from diagnostics/ with Go's standard library. Go is only present in the build stage; the final image receives a static executable. The build runs its unit tests on the build platform and cross-compiles for the target architecture.

cd diagnostics
go test -race ./...
go vet ./...
# From the repository root, after building the image:
IMAGE_NAME=hytale-server:test sh ci/test-diagnostics.sh

Keep report fields allowlisted: do not add raw errors, arbitrary configuration, process arguments, filenames, account identifiers or log excerpts. Tests use synthetic secrets and fail if these appear in the serialized report. New checks must distinguish absence, an observed failure, and facts that cannot be established without contacting or changing a running server. Keep network checks opt-in and never use them to refresh credentials or mint a game session.
